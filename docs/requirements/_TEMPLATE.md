# REQ-YYYY-NNN 需求模板

> 需求文档是「从业务问题到功能清单的桥梁」。  
> 写需求时**只描述业务意图**，不写实现（不写组件名、不写 store、不写 API path）。  
> 改功能清单必须先把对应需求 ID 写进 impact 表。

## 标题
一句话说清要解决什么业务问题。

## 背景
- 当前痛点：用户/业务现在怎么不方便
- 触发原因：为什么现在做
- 不做的后果：业务侧会丢失什么

## 业务目标
- 业务指标（可量化）：N 天 / N 人 / N 元 / N%
- 验收口径：谁在什么场景下能/不能做什么

## 影响范围（impact）
- 一级影响（核心）：哪些功能模块/子项直接被改
- 二级影响（外延）：上下游、依赖方会怎么变
- 非目标（out of scope）：明确不做的事，防止范围漂移

## 业务约束
- 合规 / 安全 / 审计
- 跨部门协作 / SLA
- 多租户场景下的隔离要求

## 验收
- 业务验收：业务方在 UAT 环境能否完成目标动作
- 数据验收：关键指标的变化方向
- 回归：旧功能不退化

## 变更历史
- YYYY-MM-DD：作者，原因
